## 0. Purpose and non-negotiable boundaries

This document defines the **exact nature, relationships, repeatability and expected outcomes** of the synthetic data needed to demonstrate all approved Hubfares POC features. It does **not** authorize new product requirements, real integrations or an alternative technical stack. Each scenario must be independently replayable, must respect tenant access, and must produce data that agrees across OTA, Operations, Admin and CXO screens.

**The implementing agent must generate and validate actual fixture files and database seed scripts** from this specification. This document is not an assertion that those assets already exist.

### 0.1 Fixed product decisions carried into all fixtures

1. B2B only. Hubfares owns the platform; separate OTA agencies are tenants. No end-customer/B2C portal.
2. `SABRE` is a **mock** GDS in Phase 0. Travelport and Amadeus have adapter placeholders/guided previews only. No credentials and no actual supplier calls.
3. An F (functional) action changes the shared SQLite demo state; G (guided) uses controlled data/results; R (roadmap) shows a labeled nonfunctional preview.
4. Agency-admin downstream markup rules **save only UI state**. They must **never** change core Hubfares search price, booking, wallet, refunds or CXO metrics.
5. Advanced commercial expressions such as `5*BF` and `1*TF` are draft strings **not evaluated**. Only simplified Hubfares-to-OTA commercial policies affect **new quotes**.
6. Currency selector supports INR, USD and EUR as **display-only equivalents**. INR remains the base offer/booking/wallet/credit/settlement currency.
7. There are **exactly two** fare-rule profiles: `A_FLEXIBLE`, `B_RESTRICTED`. No third profile and no screen-specific shadow copies.
8. The six downloadable XLSX reports are **frozen example extracts**, not dynamic SQL reports. Authorized OTA exports contain **only that agency's rows**. The passbook and CXO dashboard instead reflect live demo database mutations.
9. The assistant is an OTA-only **scripted menu-driven** support chatbot. A chatbot claim/complaint creates a case, but **never directly cancels a GDS booking or credits a wallet**.
10. Document extraction is a different step from simulated PAN/Aadhaar verification. Extracted text does not warrant a green Verified tick.
11. Simulated confirmations must always be labeled `DEMO`, `SIMULATED`, or `SAMPLE`; never imply real KYC, GDS, payment or FX calls.
12. Use fictional company/contact/passenger data only. Never use actual PAN, Aadhaar, credit cards, real bank account numbers or customer identity documents.

### 0.2 File ownership and format

- `01_PRODUCT_SPEC.md` is authoritative for workflow and F/G/R classification.
- `02_TECHNICAL_DESIGN.md` is authoritative for schemas, API routes, ledger transactions and price formulas.
- **This file** is authoritative for fixture identities, values, mock cases and seeded demonstrations.
- `04_BUILD_TEST_DEMO.md` is authoritative for test commands, execution order and test-case IDs.
- For **new, unlisted** material inconsistencies (beyond the explicit post-audit clarifications in Product Spec §13.1), **record the exact conflict and stop the affected functionality**; do not silently choose an alternative.
- All literal sample money values below are expressed in **INR major units** when prefixed `INR`, and in **integer paise** when suffixed `_minor`.
- JSON files are source fixtures; the application loads and validates them into its **single** SQLite demo database. Do not create another independent mutable data store for dashboards.

## 2. Demo clock, date arithmetic and determinism

A one-day POC may be shown on a different date from when fixtures are written. Avoid hardcoding soon-to-be-past flight departures in the live demo.

### 2.1 Anchor model

- `DEMO_CLOCK_MODE=system`: when seeding/resetting, capture **one** `anchorUtc` instant; generate all relative fixture timestamps from that one instant and persist it in `demo_metadata`. No per-record `new Date()` calls during seed generation.
- `DEMO_CLOCK_MODE=fixed`: supply `DEMO_FIXED_NOW` as an ISO-8601 UTC instant for repeatable tests. For examples only, use `2026-11-19T12:00:00Z` as a test anchor; it is **not** a required production/demo date.
- Use `D+n` for `anchorUtc` plus `n` days and `H+n` for `anchorUtc` plus `n` hours; all derived instants are UTC. Flight display must convert to airport-local time, respecting IANA zone.
- For boundary tests, generate departure at `now+1h59m59s`, `now+2h`, `now+23h59m59s`, `now+24h`, `now` and `now-1m`. Compare **instants**, not rounded minutes.
- Store calendar dates/ISO timestamps as values and **never** put unparsed `D+7` strings into the runtime DB.
- Every simulator response must be a pure function of its input, fixture version, and explicitly controlled scenario switch. No `Math.random()`-dependent results, timing or PNRs.

### 2.2 Re-seeding safety

- Reset requires a typed confirmation and Super Admin permission; runs only in mock mode against the designated local demo DB.
- Perform reset transactionally: clear mutable seeded data in reverse dependency order, restore fixtures, rebuild derived records, verify invariants, then allow login/navigation.
- Keep frozen XLSX binaries unchanged across repeated UI actions or reset, unless the explicit fixture version changes.
- Tests use an isolated temporary DB; they must never mutate the operator's rehearsed demo DB.
- A seeding failure must fail closed with a diagnostic and **must not leave half-seeded wallet or bookings**.

## 6. Core commercials, OTA markup UI and advanced draft examples

### 6.1 Executable **Hubfares-to-OTA** simplified commercial rules

Only this rule family can affect new quote pricing in the POC. Base formula from Technical Design:  
`sellMinor = supplierBaseMinor + supplierTaxMinor + fixedFeeMinor + roundHalfUp(supplierBaseMinor * percentBps / 10000) + disclosedServiceFeeMinor`.

Use these **demonstration** rules:

| ID | Match criteria | Fixed fee | Percentage | Other | Rank |
|---|---|---:|---:|---|---|
| `core_global_default` | Global | INR 200 | 0 bps | service fee INR 0 | Fallback |
| `core_sky_bom_del` | Skyline + AI + BOM-DEL | INR 75 | 100 bps (1%) | service fee INR 0 | Specific |
| `core_sky_bom_lon` | Skyline + BA + BOM-LON | INR 250 | 150 bps (1.5%) | service fee INR 0 | Specific |
| `core_orb_default` | Orbit, any route/airline | INR 150 | 50 bps (0.5%) | service fee INR 0 | Agency |
| `core_ast_default` | Aster, any route/airline | INR 50 | 25 bps (0.25%) | service fee INR 0 | Agency |

`100 bps = 1%`; `150 bps = 1.5%`. The selected rule order follows Technical Design §4.3 and `effective_from <= new quote createdAt`. All values store fixed fees as paise. If `core_sky_bom_lon` is selected for `brand_005_saver` with supplier base INR 25,500 and tax INR 4,500, the quote sell amount is **INR 30,632.50** (`25,500 + 4,500 + 250 + 382.50`). Booking and wallet must use exactly `3063250` paise, not the brand's source base displayed as sell price.

**Supported interactive demo:** Admin edits `core_sky_bom_lon.fixedFeeMinor` from `25000` (INR 250) to `35000` (INR 350). A **new** quote increases by INR 100; an already accepted quote or booked transaction remains unchanged. A booked snapshot retains rule ID/version.

**Profit modeling convention:** Treat any simulated agency rebate as a **separate accrued expense** with its own amount (or zero). It must not also reduce the booked sell price. No arbitrary BF/TF expression enters this computation.
